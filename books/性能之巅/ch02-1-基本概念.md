# 性能调优学习笔记：基本概念

## 1. 区分性能的基本概念：延迟、响应时间、等待时间、处理时间、吞吐量

其中最重要的是吞吐量和响应时间，一般高吞吐量就伴随着响应时间的增加；追求更低的响应时间就会相应降低吞吐量。而响应时间影响用户的体验

延迟 = 响应时间 = 等待时间 + 处理时间

> [!warning] 待修正（Claude）
> - **延迟 vs 响应时间**：书里严格区分。响应时间 = 等待时间 + 处理时间；延迟（latency）严格指其中的**等待**部分。只是工程口语里 latency 常被当成响应时间用，所以看到 latency 先确认它测的是哪一段。
> - **吞吐量 vs 响应时间**：这个此消彼长不是一直成立。使用率低的时候，吞吐量涨了响应时间基本不变；接近饱和（或者用批处理提吞吐）时才会明显拉长响应时间。可以想想 M/M/1 那条曲线。

## 2. 利用率 和 饱和率

利用率指的是资源被使用的时长占总时长的比例
饱和率指的是资源平均被使用的程度，这里我记得不太准确，请补充

> [!note] 补充：饱和度 saturation（Claude）
> 饱和度是资源**处理不过来、请求开始排队**的程度，衡量的是“有多少活在等这个资源”，而不是资源被用了多少。
> - 例子：CPU 运行队列长度（`vmstat 1` 的 `r` 列）、线程池队列深度、网卡丢包。
> - 和利用率的关系：利用率最高到 100% 就封顶了，饱和度还能继续涨。所以两台机器 CPU 都是 100%，有没有在排队要看饱和度。
> - 另外利用率还有一种“按容量算”的定义（SSD 这类能并行的设备，时间上 100% busy 不代表塞不下更多请求）。

cpu 利用率指的就是 cpu 被占用的时长占总时长的比例
负载指的就是 平均有多少个任务在占用、等待 cpu 或者在等待 io。

负载小于等于 cpu 核数，不需要特别关注
大于核数，就需要注意，如果 cpu 利用率也很高，那就说明系统负载压力过大，排队时间长会导致响应时间变长
但如果负载高，利用率低，那更可能是任务在等 io，cpu 并不是瓶颈，更应该考虑降低 io 的瓶颈

> [!note] 补充（Claude）
> - “等待 IO 也算进负载”是 Linux 的口径（D 状态任务），macOS 不算。
> - 对实时语音这类延迟敏感的服务，负载接近核数时就已经开始排队了，最好留余量，不要等超过核数才关注。
