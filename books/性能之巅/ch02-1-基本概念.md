# 性能基本概念

## 1. 一个请求的时间花在哪：响应时间 = 等待时间 + 处理时间

- **处理时间（service time）**：请求真正被处理的时间，比如 CPU 在执行代码。
- **等待时间（wait time）**：请求在被处理之前排队、等锁、等网络的时间。
- **响应时间（response time）**：从发出请求到拿到结果的总时间，= 等待时间 + 处理时间。用户感受到的就是它。
- **延迟（latency）**：书里严格指等待那一段；但工程口语里常拿它指整个响应时间。看到 latency 先问清楚测的是哪一段。

类比：去餐厅吃饭，排队等位是等待时间，厨师做菜是处理时间，进门到上菜是响应时间。

**为什么要拆开**：两者的优化方向不同。处理时间长 → 优化代码、算法、I/O；等待时间长 → 加资源、降低使用率、减少锁竞争。

## 2. 吞吐量和响应时间的关系

- **吞吐量（throughput）**：单位时间内完成多少请求。
- 负载低的时候，吞吐量上涨，响应时间几乎不变。
- 接近饱和时，吞吐量再涨一点，响应时间就会急剧上升，因为请求开始排队。
- 批处理是主动用响应时间换吞吐量：攒一批再处理，总量处理得多，但单个请求等得久。

结论：看用户体验用响应时间（尤其是 P99），看系统容量用吞吐量，两个都要看。

## 3. 利用率和饱和度

- **利用率（utilization）**：资源忙碌的时间占总时间的比例。回答的是“它忙不忙”。
- **饱和度（saturation）**：资源处理不过来、排队等它的工作有多少。回答的是“有没有人在等”。

关键区别：利用率最高到 100% 就封顶了，饱和度还能继续涨。两台机器 CPU 都是 100%，一台没人排队，一台队伍很长，后者才是真正的问题。**延迟变差的直接原因是饱和，不是利用率高。**

类比：超市收银台。利用率是收银员忙不忙，饱和度是后面排了多少人。

## 4. 落到 CPU：使用率和负载

- **CPU 使用率**：就是 CPU 的利用率，CPU 被占用的时间比例。
- **负载（load average）**：平均有多少个任务正在用 CPU 或在等 CPU。Linux 还会把等磁盘 I/O 的任务（D 状态）算进去。三个数分别是 1、5、15 分钟的指数加权平均，可以看趋势。负载近似反映 CPU 的饱和度。

负载要**和 CPU 核数比**才有意义。两个指标结合着判断：

| 使用率 | 负载 vs 核数 | 说明 |
|---|---|---|
| 低 | 低于核数 | 空闲 |
| 高 | ≈ 核数 | 刚好跑满，还没排队 |
| 高 | 明显高于核数 | CPU 不够用，任务在排队，响应时间变长 |
| 低 | 明显高于核数 | 任务多半在等 I/O，CPU 不是瓶颈，去查磁盘 / I/O |

注意：打开很多程序不等于负载高，睡眠中的任务不算负载。延迟敏感的服务（如实时语音）在负载接近核数时就该关注，不要等超过核数。

## 一句话讲给别人

> 响应时间 = 排队等待 + 真正处理。利用率看资源忙不忙，饱和度看有没有人在排队，延迟变差是因为排队。CPU 上，使用率是利用率，负载近似饱和度：负载要和核数比，使用率高且负载超核数是 CPU 瓶颈，负载高但使用率低多半是在等 I/O。
